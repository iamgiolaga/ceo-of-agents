# Contributing to ceo-of-agents

Thanks for helping. This plugin is mostly Markdown: skills in `skills/`, templates in `templates/`, department entries in `catalog/`, schemas in `schemas/` and upgrade notes in `migrations/`. The design spec is [docs/design.md](docs/design.md).

By taking part you agree to the [code of conduct](CODE_OF_CONDUCT.md). To report a security problem, do not open an issue: see [SECURITY.md](SECURITY.md).

## Issues

Use the issue forms: bug report or feature request. For a bug, say which plugin version you run (`/plugin`, Installed tab) and what you expected. Keep examples generic: placeholder names such as `ACME` or `BOLT`, never real companies, people, accounts or private data.

## Pull requests

- One topic per pull request, from a branch. Link the issue it closes (`Closes #12`).
- Pull requests are squash merged, so the pull request title becomes the commit on `main`. The title must follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/); a CI check fails otherwise.
- Do not bump versions or edit `CHANGELOG.md` by hand: releases do that (see below).
- If your change alters files that an existing hq holds (anything rendered from `templates/` or `catalog/`, or a schema), say so in the pull request. The release that ships it needs a migration (see below).

### Title format

```
<type>(<optional scope>)<optional !>: <summary>
```

| Type | Use for | In a release |
|---|---|---|
| `feat` | A new capability for users of the plugin | Minor bump, listed under Features |
| `fix` | A bug fix | Patch bump, listed under Bug fixes |
| `perf` | Faster or leaner behaviour | Patch bump, listed |
| `revert` | Reverting an earlier change | Patch bump, listed |
| `docs` | README, design spec, docs only | No release |
| `chore`, `refactor`, `test`, `build`, `ci`, `style` | Maintenance | No release |

- A breaking change adds `!` before the colon (`feat!: rename the setup command`). Before 1.0.0, a breaking change bumps the minor version.
- The summary is lowercase after the colon, in the imperative, with no full stop at the end: `fix(init-fleet): accept the settings file that install writes`.
- Scope is optional, lowercase, for example a skill name.

### Checks

CI runs on every pull request and on `main`:

| Check | Script |
|---|---|
| Pull request title is a Conventional Commit | `.github/workflows/pr-title.yml` |
| Every JSON and YAML file, and every Markdown frontmatter, parses | `scripts/ci/check_syntax.py` |
| Plugin manifest and marketplace file are valid and agree; every skill has a name and description; every marked version line matches `plugin.json` | `scripts/ci/check_manifest.py` |
| Every version has its migration file and its entry in `migrations/README.md` | `scripts/ci/check_migrations.py` |
| Relative links and anchors in Markdown resolve (external links are not checked, to keep CI stable) | `scripts/ci/check_links.py` |

Run them locally before pushing (Python 3.9 or later and PyYAML):

```sh
python3 -m pip install pyyaml
python3 scripts/ci/check_syntax.py
python3 scripts/ci/check_manifest.py
python3 scripts/ci/check_migrations.py
python3 scripts/ci/check_links.py
```

If you have Claude Code, `claude plugin validate .` is a useful extra check of the plugin layout.

## Every version ships a migration

An hq generated by the plugin records the framework version it was made with. Updating the plugin never changes an hq: the hq's chief of staff applies `migrations/<from>-to-<to>.md`, one step at a time, after the user's OK. So every version, even one that changes nothing in an hq, ships:

1. `migrations/<previous>-to-<version>.md`, with the exact edits, the reason for each and the checks to run afterwards. A version with no hq changes still gets a short file that only bumps `framework_version`; see `migrations/0.8.0-to-0.8.1.md`.
2. A paragraph in `migrations/README.md`, "Current status", that starts with ``Version `X.Y.Z` `` and names the migration file.

`scripts/ci/check_migrations.py` fails if a listed version has no migration file, if a file skips a version, or if the version in `.claude-plugin/plugin.json` has no entry.

## How releases happen

Releases are automated with [release-please](https://github.com/googleapis/release-please). Configuration: `release-please-config.json` and `.release-please-manifest.json`.

1. Every merge to `main` updates one open release pull request, titled `chore: release X.Y.Z`. It computes the next version from the Conventional Commit titles merged since the last release, bumps the version in every file that carries it, and adds the entry to `CHANGELOG.md`. A `docs`, `chore` or `ci` merge alone opens no release.
2. Before merging the release pull request, a maintainer merges a pull request titled `docs: add migration <previous> to X.Y.Z` that adds the migration file and its `migrations/README.md` paragraph for that exact version (see above). It may also add a sentence for the version to the status paragraph at the top of `docs/design.md`.
3. GitHub does not start workflows on pull requests opened by the Actions token, so CI does not run by itself on the release pull request. Run it by hand before merging: Actions, CI, Run workflow, on the release pull request's branch (it starts with `release-please--`).
4. A maintainer merges the release pull request. release-please then creates the tag `vX.Y.Z` and the GitHub Release with the changelog entry as notes. Users get the new version with `/plugin`, Installed tab, Update now.

To release a specific version (for example `1.0.0`), add the footer `Release-As: 1.0.0` to the body of a squash commit on `main`.

The files that carry the version are listed under `extra-files` in `release-please-config.json`: `.claude-plugin/plugin.json` and the lines marked `x-release-please-version` in `skills/init-fleet/SKILL.md`, `schemas/org.yaml` and `docs/design.md`. If you add a place that states the current plugin version, mark the line the same way and list the file there; `scripts/ci/check_manifest.py` checks that every marked line matches `plugin.json`.

Tags and releases for 0.1.1 to 0.11.0, which shipped before this flow, are created by `scripts/backfill-releases.sh` (a dry run unless called with `--apply`).
