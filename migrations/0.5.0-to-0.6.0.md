# Migration 0.5.0 to 0.6.0

Version 0.6.0 lets the fleet keep a product's repos, issues and roadmap current as it works, with standing rules instead of hooks or schedules:

- A registry of product repos. `repos:` in `org.yaml` lists each repo by GitHub slug (`owner/name`; owners may differ), with a short role, its visibility and which one is the issues home for cross-cutting issues (it may be the hq). Charters, agents and skills read the registry instead of copying repo lists. Local clone paths differ per machine, so they go under `repo_paths` in the untracked `accounts.local.yaml`; the CoS asks for missing ones at session start, as it already does for forbidden connectors.
- An optional roadmap tracker. `tracker:` in `org.yaml` names a GitHub Project (owner, number, status field), or `none`.
- A standing rule. Every change checks and updates the tracker and its issues. Issue, Project item and field, label, milestone and comment writes are free (they already belong to `issues-and-labels` and `comments`; no gate id changes). Product repos own their technical facts, and public repos receive no internal names, codes or hq content.
- Skills (no hq edit needed): `intake` gains an issue route, `record-decision` creates and updates issues and Project fields, `weekly-brief` reads the tracker, issues and PRs read-only with `gh`. All of it is skipped while `repos` is `[]` and `tracker` is `none`.

Schema change: `org.yaml` goes from `org/2` to `org/3` (two new required keys). `company/state.md` stays `state/1`.

Why `accounts.local.yaml` keeps its name: renaming an untracked file cannot travel through git, so every machine would need a manual move, and a missing file makes the CoS ask the connector question again. The file gains one key instead.

An hq that is not migrated keeps working: the skills read an `org/2` file as `repos: []` and `tracker: none` and skip the new steps. What it misses is the registry and the standing rule.

## Filling the registry

After the commit, the CoS offers to fill `repos` and `tracker` with the CEO, using the product repos and roadmap board questions of the setup wizard (question 10 in `skills/init-fleet/SKILL.md`), including the list of built-in Project workflows to switch on. Repos already named in `company/state.md` or in a charter are proposed for confirmation, never added silently. The registry is a list of facts: filling it needs a one-line confirmation and an hq commit with notice, no decision card. At the next session start on each machine, the CoS asks for the local clone paths (`repo_paths` in `accounts.local.yaml`, not committed).

Tracker writes need `gh` signed in with the `project` scope. If it is missing, the CoS adds an A item with the exact command, for example `gh auth refresh -s project`.
